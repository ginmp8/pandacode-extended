# PandaCode — working notes

## Project and releases
- PandaCode is open source (the MIT-based PandaCode License in `LICENSE`, which requires forks to credit PandaCode) with no accounts, license checks or telemetry; keep it that way. Never add code that phones home, and never commit secrets or personal paths.
- Follow [docs/VERSIONING.md](docs/VERSIONING.md) and [docs/releasing.md](docs/releasing.md): `npm run release:version -- X.Y.Z`, write `releases/extended/X.Y.Z.md`, and validate the candidate. The reviewed packaging process is local-only; automatic release publication is disabled. Create `vX.Y.Z` or publish artifacts only when the user explicitly asks to ship.
- Contributor setup and PR process: [CONTRIBUTING.md](CONTRIBUTING.md). CI is `.github/workflows/ci.yml`.
- The current 0.6.0 candidate preserves the previous Extended integrations and adds upstream 0.3.49 Connect and 0.3.50 traces. The historical 0.5.1 candidate added upstream 0.3.48's centered harness-handoff disclosure. It combines the 0.3.42–0.3.47 integration, the historical 0.3.28–0.3.42 review and the [review before 0.3.28](docs/upstream-parity-before-0.3.28.md). Follow both historical feature maps and their explicit security exclusions; keep the technical version at 0.6.0 and the display version at 0.6.0+pc.0.3.50. Earlier evidence supplements the newer provenance instead of replacing it. Jev credential hydration must stay off blocking startup; pending or failed credentials never enable features or authorize overwriting recovery data.

## Verify
- `npx tsc --noEmit` — typecheck (also runs inside `npm run build`).
- `npm test` — Node unit tests (`tests/*.test.mjs`).
- `npm run test:release` — release script tests (`scripts/release/*.test.mjs`).
- `npx playwright test` — browser suite against the Vite preview (`npm run dev` on 127.0.0.1:1420 is started/reused automatically; needs Google Chrome at `/Applications/Google Chrome.app`). A server already on the port is reused even if it serves another checkout, so in a second worktree set `PW_PORT=<free port>`. Full run ≈ 3.5 min at the default 4 workers (`PW_WORKERS=N` overrides); pass file paths or `-g "title"` for a subset.
- `npx playwright test -c playwright.webkit.config.ts` — the same suite in WebKit (the real target is WKWebView).

## UI conventions
- Color: never write a literal accent color. Use `--accent`, `--accent-rgb` (for `rgb(var(--accent-rgb) / a)`), `--on-accent` (text on accent fills), `--accent-dim`/`--accent-ink`, `--focus`, `--accent-hover`, `--accent-tint`. `src/palette.ts` sets them from the user's choice (wallpaper accent from `src/wallpaper-accents.ts`, classic yellow, a swatch) or from an imported VS Code theme (`html[data-vsix]`, mapped in `src/palette-core.ts`), which also sets the surface tokens and holds still when wallpapers change. Themes are imported natively by `vsix_themes.rs` (colors only, nothing executed). Regenerate `wallpaper-accents.ts` when scenes change; `tests/palette.test.mjs` checks every scene and 23 recorded real themes for contrast.
- Material: every floating surface (dialog plate, menus, toast) is one glass defined by the `--glass-*` tokens in `src/motion.css`: a solid translucent fill over a backdrop blur, with no top highlight, edge or `--glass-ring` outline. Reduced transparency/contrast rules must keep solid fallbacks.
- Flat: no gradients or borders; separate with surface tone (fills such as `--fill-hover`, `--surface-*`, `--raised`), spacing and radius. Masks, the trace shimmer and focus rings are excepted, and Increase Contrast / forced colors may restore lines.
- Motion: subtle and never in the way. `MOTION = true` in `src/motion.ts` drives surfaces (dialogs, toast, panes; menus arrive via `popover-motion.ts` and leave at once) with short critically damped springs: a few pixels of travel, ~120–220 ms of visible movement, exits ~120 ms; input is never gated and every caller keeps an instant path (`MOTION = false` makes the app instant again). CSS transitions are limited to color, background, opacity, box-shadow and `scale`/`rotate` in 100–200 ms; never animate layout (width, height, grid, top/left). `prefers-reduced-motion: reduce` removes CSS transitions and animations (`styles.css`, `overlay.css`) and motion.ts keeps only a short cross-fade. The live tool trace (`src/trace-motion.ts`, `src/trace-motion.css`) choreographs more: steps blur in, the two newest result cards unfold (older ones fold), the header mirrors the running step with a shimmer, and the turn folds to its summary at the end, with @keyframes and the Web Animations API; the action dock (`src/action-dock.ts`) follows the same rules. Press feedback uses the `scale` property, never `transform`, so a button positioned with `transform` stays under the pointer while pressed. Sidebar task rows are `.task-row` wrappers holding the `.task-item` and its `.task-actions` (the `.task-more` row menu); the selected row has a slim accent bar at its leading edge. The toast (`notify()` in `main.ts`) is warm glass in the bottom-right corner, max 360 px, wraps and clamps, and waits while hovered.
- Action dock (`#action-dock`, `src/action-dock.ts` + `src/action-dock.css`): the workspace header's actions are one `role=toolbar` glass pill of 38px items (`--dock-item`; 28px under 640px tall, 26px under 520px) in `--glass-warm` with the header's own `var(--header-blur)` (`--header-glass` over a wallpaper) at the main pane's right edge (left of an open inspector, at the window edge when it is closed; left of the overlay inspector at 651–920px), vertically centred by `placement()` in the free space between the header (or open file tabs) and `#composer-area`, 12px clear of both, re-placed by a ResizeObserver (pane, composer, file tabs, main pane, dock) and on resize. Groups (panels: inspector, terminal, browser, moodboards, Agents · actions: Run, Deploy, Task actions · update prompt `#update-status` + Later) are split by a 20×2 rounded bar of `color-mix(in srgb,var(--text) 20%,transparent)`, which folds in and out with a lone group's item (its `::before`, animated through `pseudoElement`); while the dock's own height springs, the centring follows it frame by frame. The header keeps only its leading items and `.header-actions` (the preview note). `--dock-clear` (58px) narrows the transcript, file tabs, task details, JEV activity, file view and composer column (not on the New task page) so nothing clickable sits under the dock; a shared bot channel never runs under the header (`.channel-thread` is excluded from `--header-under`), so its settings button stays in its own row. At ≤650px and in the board/GitHub views the same element is a `position: relative` row in the header (`--dock-clear: 0`). Items keep their ids, names and `data-action`; other modules still toggle `hidden`, `active` and `title`, and the dock's MutationObserver moves each `title` into `data-dock-tip`, springs items in/out on `hidden` (height in a column, width in a row; a leaving item is `inert` with `data-leaving` until it collapses, and its group stays until then), and grows/fades the active accent fill (`::before`; several panels can be on). One shared `.action-dock-indicator` pill slides to the hovered or keyboard-focused item on its own softer `PILL_SPRING` (damping .85, response .28 ≈ 367 ms), dissolves (`data-muted`) over an active item so it never pops under the accent fill, and fades out on leave. The label bubble (`#action-dock-tip`, the same glass and `--header-blur`, mounted in the header beside the dock so its blur sees the thread) waits 350 ms on hover, shows at once on keyboard focus or while another is up (300 ms grace), slides and resizes between labels, sits left of the dock or below the row (kept inside the window), and Escape hides it without reaching the app. One spring (`DOCK_SPRING`, damping .85, response .2 ≈ 267 ms); hover scales the icon to 1.05, press to .94 (the icon only on `aria-haspopup` triggers); the entrance (16 ms stagger) plays once per window session (`sessionStorage`) after the composer lays out, and startup renders before the first press or key never animate. Roving: one Tab stop, ↑/↓/←/→/Home/End. Spec: `tests/action-dock.spec.ts`.
- The `<dialog>` stays transparent and untransformed: `.dialog-plate` behind it carries the glass, `.dialog-scrim` dims, and a closed-shadow-root ghost carries the exit. Never put `backdrop-filter`/`transform` on the dialog itself — menus opened inside it are `position: fixed` in viewport coordinates.

- Queue and steering: while an agent runs, Enter queues (`queue_*` commands, shown by `src/message-queue.ts` above the composer) and ⌘/Ctrl Enter steers (`steer_task` → `RunInput::Steer`, `providers/steering.rs`). Steering never stops a run: Claude-family harnesses steer on stream input (launched with `--replay-user-messages` so a late steer keeps the run open for its turn), Codex uses `turn/steer`, Pi `steer`, OpenCode a second `session/prompt` (`acp.rs`); anything a turn cannot take (startup, between turns, refused, other ACP agents) is held by the run and sent as the next turn of the same session (`mode: "next-turn"`). `steer` agent events report `pending`/`delivered`/`failed` by id; the composer shows the pending state and requeues a failed steer. A clean run end delivers the next entry; a failure, stop or restart holds the queue until Resume. The prompt stays enabled during runs, so `renderComposer` must keep focus and the caret. The wider roadmap is in `docs/parity-plan.md`.
- Remote access, PandaCode Connect ([docs/remote-access.md](docs/remote-access.md)), is opt-in: there is no network traffic until GitHub sign-in (device flow). The relay is `relay/`, a Cloudflare Worker with one SQLite Durable Object per account, hibernated WebSockets, and GitHub app-checked sign-in. It forwards only X25519 + XChaCha20-Poly1305 ciphertext. The native side is `src-tauri/src/remote*`: a host answers only devices pinned in its trusted list, and only while "Allow remote control" is on. All encrypted request/response/event frames carry `ts`/`nonce` against replay; both peers must use the hardened revision. A task can *run on another computer* as a mirror: an ordinary local session row with `remote_device`/`remote_session`/`remote_synced_id` (schema 26), started by `remote_start_task` (host side `remote/start.rs` finds or clones the GitHub project into `~/PandaCode`). Agent commands for a mirror (`send_message`, `stop_session`, approvals, input, `steer_task`, model/effort) are routed natively by `remote::route`; the queue stays local. Hosts push raw `AgentEvent`s (`agent.events`, one frame per subscriber per 100 ms, text deltas merged, then `run.finished`), which the viewer re-emits as `agent-event` under the local id, and messages are copied with `task.messages` after each run (`remote/mirror.rs`). `Store::workspace_root` refuses a mirror (`This task runs on <name>.`), so git, worktree and file commands never touch the local disk. There is no remote view. The UI is `src/remote*.ts`, with mocks in `src/preview-remote.ts`. Builds need `PANDACODE_RELAY_URL` and `PANDACODE_GITHUB_CLIENT_ID`.
- Bots (docs/bots.md) live in `src-tauri/src/bots*` and `src/bots*.ts`. Each bot owns a workspace project and each conversation is an ordinary task, so `run_finished`/`approval_requested` hooks in `lib.rs` route replies and approvals back to channels. Bots are listed in the sidebar's Bots section (`renderBots` in `main.ts`, from `bots_list`, which includes each bot's `desktopSession`); a row opens that conversation via `bot_desktop_thread` in the ordinary conversation pane: the same transcript, streaming, composer and model picker as any task (a model chosen there is saved on that conversation with `configure_session`; the bot's profile model applies to new conversations). `botForThread()` in `main.ts` finds the bot for any thread in its workspace, so the header shows `botCrumb()` (name, state, pause, Settings), an empty thread shows `botWelcome()`, the prompt reads "Message <bot>…", and the `.bot-thread` class hides the project bar; these styles live in `styles.css` because they render before the bots module loads. Settings are a modal (`showBotSettings`, `mountBots` with `layout: 'settings'`): Profile, Conversations, Memory, Schedules, Channels, Rules and Activity, styled by `src/bots-settings.css`; the Bots window (`layout: 'window'`) is the same body beside a bot list and creates bots, which then open in their conversation. There is no separate bot chat view. Prompts typed in a bot's own conversation go through `bot_message` so the brief and memories apply; the brief folds behind the message's attached context. Bot workspaces stay out of the project tree, filter and picker (`userProjects()`). Bot tasks drain their queue natively; the window skips `dispatchQueue` for bot projects. Channel secrets stay in the keychain via `bots/secrets.rs` and never reach the webview. The local server (`bots/channels/http.rs`) binds 127.0.0.1 only and checks the Host header for web chat.

- Model routing ([docs/model-routing.md](docs/model-routing.md)): Panda Router (v4) runs natively (`src-tauri/src/panda_router.rs` + `panda_router/`: ONNX int8 profiler via `ort`, `tokenizers`, deterministic MIRT matcher over model cards, success head, policy with an escalation ladder; `model_routing.rs`: settings, download, IPC; `src/model-routing.ts`). The profiler files come from `raw.githubusercontent.com` at a pinned commit of `aicodeking/PandaOrchestrator` and are sha256-verified; bumping the commit means updating the hashes (in `ASSETS` and the CI `router` job) and `panda_router::ASSET_DIR`, with the old directory added to `OLD_ASSET_DIRS` in `model_routing.rs` (deleted once the new files load). Settings default to Balanced with min P 0.5 (clamped 0.3–0.9, on P's lower bound); `Settings.version` marks files saved since v4, and in an older file a saved 0.8 (the old default) becomes 0.5. Download happens only while routing is on, when a team turns on or first routes, or on an explicit Settings click, never at launch, and never on macOS < 13.4 (`unsupported_os`; the bundled ONNX Runtime targets 13.4); `ort`/`tokenizers` link only where `cfg(panda_onnx)` holds (Apple-silicon macOS, arm64 Linux, Windows; same predicate in Cargo.toml and `build.rs`), so Intel Mac and x86_64 Linux builds use `panda_router/onnx_stub.rs` and the heuristic, and CI's macOS `router` job checks tokenizer ids and well-formed ONNX output (numeric parity varies by CPU, so it is opt-in with `PANDA_ROUTER_STRICT=1`); a profiler that verifies but cannot load stays on the heuristic for the process (`unusable`), with no re-downloads; dispatch and `route_models` never wait for it and use the keyword heuristic until it is ready. With routing off, `profileId: "auto"` falls back to the lead's model rather than failing. The composer's Team button (`showTeamMenu` in `main.ts`) offers No team and, while routing is on, Cheap/Balanced/Best team, each setting the one global mode with `model_routing_configure` (a running auto team's label and next routed dispatch follow it) and turning on an automatic team (`setTeam`); main.ts caches one `RoutingStatus` (one shared in-flight `loadRouting()`, retried on focus and on render until loaded, at most every `ROUTING_RETRY_MS`; changes take a `routingTicket`, reads take none and land only if no change started since or is pending, so a read never overrides a change), and `src/model-routing.ts` announces each status it renders (newest request only) as a `pandacode:routing` window event so only the Team button updates. The lead's `profileId: "auto"` routes over the team's `catalog` (all models of installed harnesses, up to 1000, rebuilt when a team turns on), not the 24-entry roster; named agent teams stay within their roster. A fresh `auto` worker in Balanced is staffed on `route.ladder[0]` and in Cheap on the first rung whose lower bound clears min P (the opener; else, and in Best, the policy pick; `routing::staff`, note `ladder 1/N, opener; policy pick …`). Escalation: a dispatch assignment's `replaces: <worker ID>` (a worker that failed, or completed with a result that failed the lead's check; optional `replaceReason`; stopped/unfinished and already-replaced workers are refused) abandons that worker, and with `auto` routes with `failed` = the whole chain of models that failed the assignment (rebuilt from the saved `architect_requests` by `routing::failed_chain`, no worker field), so the pick never steps down; a chain of `routing::MAX_ATTEMPTS` (3) refuses any further replacement (auto or hand-picked) and tells the lead to report to the user; `route_models` returns `decidedBy` and the first 4 ladder rungs. Cards without data are unrated and never auto-picked. Model health (`model_health.rs`, docs/model-routing.md#unavailable-models-and-failover): harness errors pause a model per harness (saved in app data, two paused models pause the harness until a success), paused models never reach the router, and a failed team worker fails over to the same model on another harness; Settings lists them with Allow now.
