## Architecture and user-facing operation

- **Direct conversations:** Open the existing Team/Council panel. The default is automatic/native reviewers. Select 2–8 distinct eligible configured bots to use Selected bots for this task; the executor cannot be a reviewer. Native Council still owns rounds, score thresholds, correction and reports. No separate Council or bot type is created.
- **Task authority:** A selected bot supplies frozen ID, persona, model/harness, selected skill receipts and effective task/phase permissions. Review starts read-only. Exact authorized host actions do not copy ambient bot grants, shell, arbitrary MCP access, credentials or unrestricted write access to a reviewer seat. Unsupported requests fail visibly.
- **Task-scoped skills:** Only explicitly assigned central-library skills and required dependencies are eligible. Native authority records provenance, content hashes, mandatory/optional role and evidence status. Skill import is not activation; a model claim is not execution proof. Files are content-addressed and read-only outside the assessed checkout. Changes to the library affect later rounds, not a live frozen round.
- **Shared Channels:** An actionable user message explicitly opts in to Council for that delivery. Council-disabled deliveries retain ordinary routing. One message to two executors has two independent cycles; later messages and the bot's desktop chat do not inherit task Council settings. The originating channel displays approval state, attributed acceptance, visible recovery and safe skill provenance, not private reviewer transcript contents.
- **Completion and follow-up:** A successful channel reply requires the matching fresh native Council pass with mandatory evidence, or a separately reasoned and attributed user exception. Waiting, low score, limit, denial, stale change and stopped are not approval. The terminal delivery claim and callback are idempotent. An optional GitHub issue is created by the same bot only after approval and only under the original explicit repository/action grant. An uncertain external result is reported as unknown and is not blindly retried.
- **Recovery:** Restart and resumptions preserve per-delivery Council linkage and stored authorization. Removed/paused reviewers, archived channels and unsupported provider failover remain blocked; no implicit privilege broadening or automatic external replay.

See [S2 selected bots](council-selected-bots-s2.md) and [S3 frozen skills](council-reviewer-skills-s3.md) for configuration and provenance details.

## Deferred manual validation checklist (English; not a code-stage gate)

Run these *after* all S2–S7 code has shipped, if the owner chooses to collect real-service evidence. Record OS, PandaCode SHA, harness/provider names and versions, selected bot IDs (redacted externally), sanitized screenshots, native state/cycle IDs, expected/observed outcomes and timestamps. Never disclose tokens, MCP secrets, private transcript contents or local credentials.

1. **Baseline direct Council:** In an ordinary bot chat, run automatic Council; check existing scores, correction and report UI. Verify no unexpected bot profile or conversation change.
2. **Selected direct Council:** Select two distinct available configured bots with independent supported harness/model settings. Run an actual task; verify independent reviewer sessions, scores, names and rounds. Attempt executor self-review, duplicate, paused, removed and unavailable reviewers; each must fail visibly.
3. **Permission enforcement:** On a real supported harness, attempt default reviewer checkout writes, shell and unauthorized MCP/external actions; deny. Grant one exact task-scoped permitted action, verify only that resource and phase succeeds, then verify a neighboring resource and later phase are denied. Compare protected files and bot state before/after.
4. **Skills:** Import but do not assign a skill: it must not appear. Assign a compatible, acknowledged library skill and a mandatory dependent file; verify exact source commit/hash, isolated read-only content and native receipt without global activation. Replace/sync the library and edit the bot during an active round; the first round stays pinned and the next explicitly revalidates.
5. **One Shared Channel delivery:** Enable Council on one user message only; send a second Council-off message to the same bot and a direct chat. Ensure no Council configuration, task history, transcript or callback leaks across them.
6. **Two recipients and concurrency:** Address two bots and also queue two same-bot Council assignments; confirm separate delivery IDs, cycle IDs, reviewer sessions, scores and callbacks. An unrelated channel must reveal no private context.
7. **Approval and retry:** Confirm low score, missing required check, limit and stale changes cannot complete a delivery. Verify correction rounds. Use a reasoned local-user exception and verify distinct attribution, then exactly one final channel reply.
8. **Restart/recovery:** Restart at review, correction, awaiting acceptance, callback and pending follow-up. Repeat on stopped, archived, removed/paused bot and unavailable provider. Require safe blocked states, retained provenance, no duplicate assignment/reply and no implicit external retry.
9. **GitHub follow-up:** Explicitly authorize only one test repository/action for the same executor bot. Verify zero issues before passing/accepting, exactly one after the matching approval, and no write to a second repository. Interrupt an in-flight create and inspect the repository before deciding whether to retry; an unknown result must not be silently repeated.
10. **Compatibility:** With no selected reviewers/skills and Council off, repeat direct bot chat, old Architect Council, one/two-recipient channels, queue, bot import/export and Skills Manager import/sync/Try-in-chat. Verify unchanged behavior.
