# Council S1: task-scoped native reviewer authority

## Product contract

A PandaCode bot keeps its configured harness, Skills, MCP references, Connections, and permissions. Council does not edit the bot profile. A reviewer seat runs with an **effective task- and phase-scoped policy** instead of inheriting every ambient capability. Native reviewers default to `NativeReadOnly`. A future user-facing S2/S4 flow can provide a frozen, explicitly authorized intersection of the bot's configured tools and the user's exact task grants.

A grant names an existing **host-managed function tool**, an exact operation (`action` argument, or atomic `call`), and an exact string resource argument/value. The native wrapper both advertises only granted tools and checks every invocation before dispatch, including MCP transport. Unknown, composite, absent, unscoped, or unsupported tools do not silently gain access. Full-access source bot permission alone never authorizes a reviewer write. A grant must be explicitly sourced from the user's selection, not a model prompt, skill description, or other untrusted artifact. A user-authorized operation that changes the assessed artifact must invalidate the approval; S4-S6 own revision and delivery integration.

The same bot can conduct a review and later publish GitHub issues based on accepted findings. **Issue publishing is S5**, after an approved verdict and the user's repository/action opt-in; no extra confirmation or second bot is required for an already authorized action. S1 implements the underlying grants and native execution boundary only. The current Council UI does not yet select these grants and no new GitHub publishing workflow is claimed here.

## Frozen identity and compatibility

`ReviewerBinding` contains Council cycle, optional delivery ID, round, seat, optional reviewer bot ID, artifact revision token, and immutable provider/model/lens/tool policy. Native automatically scheduled reviewers use no delivery or external bot identity in S1; S2 and S4 must bind their IDs to authoritative records. An S1-issued native artifact token is anchored to Council start, source dispatch revision, worker creation time, and worker ID; it is **not** a content hash or proof that an artifact was checked. New S1 seats also store an independently issued `architect_requests` authority record, and admission compares the exact token and tool policy to that native record. A syntactically valid but changed dispatch revision is rejected; seats created before the record existed retain only `NativeReadOnly`. A saved `Scoped` worker policy without matching trusted issuance is rejected. Legacy workers without a binding retain read-only admission. Existing WorkerProfile and native Council scoring/rounds are not replaced.

The reviewer tool catalog version is bumped so Codex's persisted native worker contexts recover without retaining an older writable tool inventory. New grants must be derived from actual configured bot capabilities by trusted native code; S2 will own collecting and resolving user grants. A future trusted native user-action adapter may update the independent authorization record only with the exact configured/requested grant intersection. S1's normal dispatch always issues `NativeReadOnly` and cannot be promoted merely by modifying the serialized worker. S6 will revalidate them on resume and failover.

## Enforcement boundary

- Codex review always retains its native read-only filesystem sandbox, denied network through sandboxed shell, and `approvalPolicy=never`; the bot's ordinary `Full access` mode remains unchanged.
- A scoped Council reviewer may receive only individually permitted **PandaCode-owned host tools**. The wrapper checks tool name, operation and resource argument again at invocation time. User-granted actions are preauthorized for exactly that scope; unauthorized actions are rejected. Native tools under the application's `ALWAYS_ASK` rule remain unavailable in reviewer mode, rather than silently bypassing mandatory confirmation. Generic tool and shell privileges are not conferred.
- **Provider-scoped preflight:** only Codex runs the native `codex mcp list` and project-configuration probe. Other providers must not be launched with Codex-specific arguments; they use their existing native adapters and permission handling. This routing fix does **not** establish equivalent external-MCP isolation across providers; installed-harness checks remain mandatory.
- Direct external Codex MCP servers are **not** a managed host-tool boundary. The native `codex mcp list --json` preflight requires an empty external server inventory and project-local MCP/plugin/app configuration is rejected. `-c mcp_servers={}` does not erase inherited TOML servers. Direct third-party MCP access remains unsupported until a future adapter can enforce scoped calls; never silently allow it because the bot already has an MCP reference.
- All 19 registered **local provider adapters** may now be admitted in Council's default Plan reviewer mode instead of rejecting everything except Codex. Each adapter keeps its native Plan/permission posture, and PandaCode refuses all explicit reviewer escalation requests across Codex, Claude, ACP, Pi, Muse and ZCode protocols. Claude-family execution restricts settings sources, native tools and hooks. Pi loads only the explicit PandaCode permission bridge, built-in read/search tools and no discovered extensions/MCPs; OMP disables discovered extensions, skills, rules and context files. Muse uses its native disable-write/disable-shell flags. ACP adapters require a compatible Plan mode or a client-side deny policy, with no silent write-capable fallback. Reviewer capability grants still use exact PandaCode-owned tools with native dispatch guards; ZCode has no native MCP host bridge and therefore cannot use scoped grants yet. **These are different adapter mechanisms, not a universal OS-level sandbox guarantee.** Actual authorization and filesystem isolation must be verified per installed harness/OS before marking AC-03/AC-18 complete. External or autonomously executed shell/MCP actions are not made safe merely by a protocol denial.
- A reviewer subprocess receives a bounded runtime/authentication environment (including selected provider credentials, runtime paths, certificate/proxy setup) rather than automatically inheriting all shared variables. Variables explicitly configured **for that provider** remain available as the user's intentional harness configuration; unrelated global GitHub/AWS tokens are not injected into unrelated providers. Ordinary bot runs remain unchanged. Native host tools handle their own separately authorized credentials. Credentials must not be inserted into prompts, UI results or logs.
- Skills are evidence/method inputs, never permission grants. Reviewer changes to protected Council scores, source artifact, unrelated profiles/schedules/messages or approval evidence remain unauthorized absent a precise trustworthy grant and corresponding gate.
