## Overview

This candidate brings the upstream PandaCode improvements after the 0.3.50-based Extended 0.6.0 baseline through source 0.3.94, while preserving Extended-specific GitHub/Board features, configurable feature controls, dependency remediations and upgrade compatibility. The primary user-visible changes concern the redesigned desktop experience, more capable conversations and agent orchestration, broader provider/harness integration and opt-in controls over remote or automatic operations.

## Highlights — cumulative since Extended 0.6.0

### Redesigned workspace and conversations

- **New desktop interface (upstream 0.3.92):** unified dark/light/imported-theme styling, refreshed Settings and prompt layout, live thread scenes, per-turn cards, inline diffs, and up to six tiled thread views. Multiple scenes can increase GPU use; native desktop acceptance remains pending.
- **More focused navigation:** inset conversation/inspector/Settings panels, interruption-safe transitions, searchable task/sidebar states, updated model picker, file previews and readable tool traces.
- **Side conversations with /btw:** ask a separate question alongside the main thread, retain its context and move a useful answer back to the primary prompt. Side threads have documented limitations for some remote/bot/attachment flows.
- **Execution visibility and visual feedback:** clearer tool/MCP/subagent activity and annotated visual progress snapshots for eligible UI tasks.

### Agents, models and automation

- **OpenCode V2 and ACP improvements:** model-specific reasoning/effort variants, more reliable mode fallback, and provider catalog handling; support is conditional on capabilities advertised by the installed harness.
- **Richer orchestration:** bot channels and controls, team/sub-worker coordination, per-harness model routing, scheduled work, and configurable agent/provider integrations, including ZCode and Hermes as supported by the imported source.
- **Provider and platform fixes:** DeepSeek command discovery, larger Claude catalog responses, OpenCode MCP capability inventory, Windows-style conversation import, project recovery, and Linux composer/Wayland clipboard handling.

### Remote work, machines and cloud

- **Multi-machine capabilities:** when enabled and authorized, linked computers can run coordinated agent tasks subject to device grants; Connect includes remote-history, reconnect and eligible-machine selection improvements.
- **Cloud/headless workflows:** imported cloud, VM, container, SSH and provider capabilities remain available under the applicable user permissions and Extended controls, rather than being removed solely because they involve remote operations.

### Extended-specific controls, security and compatibility

- **Configurable safety boundaries:** background app/agent update checks, Connect, credential transfer to cloud agents, agent-initiated VM/cloud changes and external MCP exposure have default-off protections for new/unset preferences; manual or explicitly enabled upstream paths remain available where permitted.
- **Bot pause and direct routes:** the global pause is optional (bots are not paused by default); LAN/Tailscale direct routing is separately configurable when Connect is enabled. Turning a feature back On must preserve the permitted upstream behavior.
- **Legacy database upgrade:** guarded SQLite migration 37 reconciles schema collisions affecting databases from Extended 0.6.x without intentionally discarding existing tasks or bots. A representative existing database still needs an upgrade test and backup.
- **Dependency remediation and release control:** Rust/mobile dependency follow-ups and security checks accompany an Extended-only publication safeguard: a tag push may build artifacts but cannot automatically publish GitHub Releases or npm packages; explicit manual publication is required.

## Upgrade considerations and known limitations

- **Existing installations:** validate the upgrade path from the last distributed Extended build before advising users to install. Back up an existing SQLite database before any migration test. The documented migration is not, by itself, proof of a safe upgrade.
- **Settings:** confirm feature controls after upgrading. Disabling credential transfer does not revoke credentials previously copied; changes to MCP permissions for new processes do not reconfigure agents already running.
- **Outstanding checks:** native Windows/macOS/Linux application and installer smoke tests, redesigned Settings On/Off behavior, real two-computer Connect, actual provider/harness effort selection, and selected GPU/tiling interactions remain unverified for the final candidate. See the [0.8.0 known-issues register](../../docs/extended/0.8.0/known-issues.md) and [release checklist](../../docs/extended/0.8.0/release-checklist.md). Unverified scenarios are not automatically confirmed regressions.

## Release identity and publication blockers

The current source manifests deliberately follow upstream **0.3.94**, not the planned Extended distribution version **0.8.0**. Specifically:

1. **Executable identity:** package.json, src-tauri/Cargo.toml and src-tauri/tauri.conf.json still declare 0.3.94; the Tauri product name, identifier and updater endpoint also retain upstream values. Confirm a separate Extended installer/upgrade/update identity before publication.
2. **Workflow mismatch:** .github/workflows/release.yml derives the release tag/version from the Tauri manifest and reads releases/{version}.md. Tagging the current tree **v0.8.0** would fail its version check, and a source-version run would use the upstream **0.3.94** notes instead of this file.
3. **Parity-validator constraint:** scripts/release/version-identity.test.mjs expects all source-version manifests to equal the pinned upstream 0.3.94 version. Merely replacing those values with 0.8.0 is not a valid isolated fix. Design and verify an independent Extended distribution identity without weakening upstream source parity.
4. **Candidate acceptance:** re-run relevant CI/build and behavior checks against the final immutable source SHA, review the inherited known issues and obtain explicit release approval. Merge to base/hardened and then main only after normal review; neither a merge nor a green CI job publishes a release.

No release is authorized or performed by this document.
